# With Bader

With Bader is an Arabic-first interview preparation and content-management application. It
organizes guests, research, interview questions and transcripts, notebooks, content drafts,
calendar scheduling, and template-based social design drafts in one authenticated workspace.

## Architecture

- `backend/`: FastAPI, SQLAlchemy 2, Alembic, Argon2 password hashing, signed HttpOnly sessions.
- `frontend/`: Next.js 16 App Router, React 19, TypeScript, TanStack Query, Tailwind CSS.
- `database/`: immutable historical SQL migrations 001-009 used by the Alembic baseline.
- PostgreSQL 16 stores application data; generated legacy design media uses a local volume.
- Groq powers configured AI/STT operations; Exa and Tavily are optional research providers.

The intended production shape is one cost-conscious server running PostgreSQL, one FastAPI
process, and one Next.js process behind a TLS-terminating reverse proxy.

## Prerequisites

- Python 3.13.x (the repository pins 3.13.6 in `.python-version` and declares `>=3.13,<3.14`).
- Node.js 24.x and npm 11.x.
- PostgreSQL 16 or newer.
- ffmpeg for audio normalization/chunking and the complete audio test path.
- Docker Desktop / Docker Engine with Compose, if using the container workflow.

## Environment configuration

No real secrets belong in Git. For Docker, copy the root example and replace every placeholder:

```powershell
Copy-Item .env.example .env
```

For local backend development, copy `backend/.env.example` to `backend/.env`. Its database URL
already targets the Compose PostgreSQL port (`localhost:5433`). Generate `AUTH_SECRET` with:

```powershell
python -c "import secrets; print(secrets.token_hex(32))"
```

Copy `frontend/.env.local.example` to `frontend/.env.local`. `NEXT_PUBLIC_API_BASE_URL` must be
an address the browser can reach, normally `http://127.0.0.1:8000` locally.

Important operational settings:

- `CORS_ORIGINS`: comma-separated exact frontend origins; local origins are safe defaults.
- `REGISTRATION_MODE`: `open` (default) or `closed`; changing it requires no code edit.
- `LOGIN_RATE_*` and `REGISTER_RATE_*`: per-IP sliding-window limits.
- `AI_RATE_*`: shared per-user limit across provider-backed routes.
- Provider names can be set to `mock` for local/testing use without external credentials.

## Local development

Start only PostgreSQL (the named volume preserves existing data):

```powershell
docker compose up -d postgres
```

Set up and run the backend:

```powershell
cd backend
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python scripts/migrate.py
uvicorn app.main:app --reload
```

In another terminal, set up and run the frontend:

```powershell
cd frontend
npm ci
npm run dev
```

Open `http://localhost:3000`; the API health endpoint is `http://localhost:8000/health`.

## Database migrations

`python scripts/migrate.py` is the supported migration entry point (run it from `backend/`). It
handles both cases safely:

- Empty database: Alembic executes the checksum-protected historical 001-009 SQL baseline,
  then all newer Alembic revisions.
- Existing manual 001-009 database: it compares the real schema with SQLAlchemy metadata,
  stamps the baseline only if they match, and applies only newer revisions. It never reruns
  historical SQL over existing data.

Revision `0002_require_guest_owner` refuses to proceed if any guest has `created_by IS NULL`;
it never guesses ownership or deletes a guest. Resolve each owner manually, then rerun.

For future changes:

```powershell
cd backend
alembic revision --autogenerate -m "describe change"
alembic upgrade head
alembic check
```

Review every autogenerated migration. Do not edit SQL files 001-009 because their checksums
are part of the reproducible baseline.

## Tests and quality checks

Backend tests use the configured PostgreSQL database and clean up their own fixture data:

```powershell
cd backend
python scripts/migrate.py
python -m pytest -q
```

Install ffmpeg before running the suite so chunking tests execute rather than skip.

The frontend quality gate intentionally builds before the standalone typecheck because Next.js
generates `.next/types` during the build:

```powershell
cd frontend
npm ci
npm run check
```

`npm run check` runs lint, build, then typecheck in that order. CI performs these same checks,
fresh PostgreSQL migration, legacy-baseline adoption, the full backend suite, and container builds.

## Docker deployment

After filling the root `.env` (including strong database/auth secrets and real public origins):

```powershell
docker compose up -d --build
docker compose ps
```

The backend container runs migrations before starting one Uvicorn process. Keeping one process
is intentional because the rate-limit store is in-process. If the API is later scaled to multiple
processes or hosts, move rate-limit state to a shared store such as Redis first. Put a reverse
proxy in front of ports 3000/8000 for TLS and request-size controls in production.

## Project structure

```text
backend/
  alembic/               migration environment and revisions
  app/api/               HTTP routes
  app/core/              settings, authentication, request controls
  app/models/            SQLAlchemy metadata
  app/services/          persistence/domain services
  tests/                 unit and PostgreSQL-backed integration tests

  app/                    Next.js routes and layouts

  services/              feature APIs, hooks, types, and components

```

## API notes

Collection endpoints keep their existing array response shape and accept `skip` and `limit`;
`skip` must be non-negative and `limit` is 1-100. Authentication remains cookie-based. Login
continues to return the same `Invalid email or password` response for unknown emails and wrong
passwords.
